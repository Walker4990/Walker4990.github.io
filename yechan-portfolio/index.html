👟 TROUBLE SHOOTING

🚨 문제 배경

출고 등록(newOutInven)은 정상 동작했지만, 출고 수정(updateOutInven) 요청 시 JMeter 부하 테스트에서 500 에러 100% 발생.

  • 평균 응답시간 297ms 이상 → 서비스 지연 심각
  • NullPointerException 발생 (stockQuantity 값 누락)
  • DB에서 풀스캔 발생 → 불필요한 부하
  • 동시성 제어 부재 → 재고 음수 발생 위험

📌 개선 방향

  • DB 인덱스 최적화 및 쿼리 조건 강화 → 풀스캔 제거
  • 출고 수정 로직 개선 → NPE 방지 및 원자적 재고 갱신 보장
  • 재무/세금/로열티는 반드시 정정 INSERT → 회계 투명성 확보
  • JMeter 부하 테스트로 사용자 수별 성능 곡선 측정

⭐ 해결 방법

1. 복합 인덱스 생성


-- Before (풀스캔 발생)
SELECT * FROM shipment WHERE inventory_no = ?;

-- After (복합 인덱스 적용)
CREATE INDEX idx_shipment_inven_sn 
ON shipment (inventory_no, shipment_no DESC);

2. 출고 수정 쿼리 보완 (단일 행 보장)


-- Before (다건 수정 위험)
WHERE inventory_no = #{inventoryNo}

-- After (단건 수정 보장)
WHERE shipment_no = #{shipmentNo}
AND inventory_no = #{inventoryNo}

3. 재고 차감 원자화 처리 (음수 방지)


UPDATE inventory
SET quantity = quantity - #{editQuantity}
WHERE inventory_no = #{inventoryNo}
AND quantity - #{editQuantity} >= 0;

4. 서비스 계층 개선 (@Transactional)


// Before
Integer authorNo   = mapper.getAuthorNo(bookNo);
Integer contractNo = mapper.getContractNo(bookNo);
BigDecimal royalty = mapper.getRoyaltyRate(bookNo);

// After
Map<String, Object> meta = mapper.getBookMeta(bookNo);

🤩 알게 된 점

  • 단순 오류 해결이 아니라 쿼리 실행계획 + 서비스 로직 + 동시성 제어까지 종합적으로 고려해야 함
  • DB와 애플리케이션의 병목 원인 구분 능력이 중요
  • 성능 개선은 단순한 속도 향상이 아니라 정합성 + 안정성 + 확장성까지 함께 보장해야 함

🚨 문제 배경

  • 대시보드 화면에서 사용하는 /getInventoryBook API는 책별 재고 수량을 집계해서 보여주는 기능이다.
  • 처음에는 단순히 DB에서 직접 조회하도록 구현했는데, 사용자가 늘어나면 같은 API가 반복 호출되면서 DB에 부하 발생.
  • JMeter 부하 테스트 결과:
    • 동시 사용자 100명 → 평균 응답속도 40ms 이상
    • 500명 이상 → 응답속도 증가 및 Throughput 한계 발생
  • 사실 데이터는 자주 바뀌지 않는데도 매번 DB에서 가져와 비효율적 문제가 있었다.

📌 개선 방향

  • /getInventoryBook API는 단순 재고 현황 조회 기능 → 매 호출마다 DB 접근은 비효율적
  • 자주 조회되지만 큰 변화가 없는 데이터 → Redis 캐시 활용
  • Spring @Cacheable 적용, TTL(10분) 설정으로 데이터 신선도 보장
  • JMeter로 캐시 전/후 성능 비교 측정 → 개선 효과 수치화

3. 급여 등록 / 지급 UX 개선

🚨 문제 배경

직원 수가 많아질수록 급여 등록을 개별 입력으로 처리하는 것은 비효율적이었고, 보너스/OT 입력 시 값이 테이블에 실시간 반영되지 않아 재입력·새로고침이 반복되는 문제가 발생.

⭐ 해결 방법

급여 담당자 UX 개선 목표: “등록 → 지급 → 확인” 과정을 한눈에 직관적으로 볼 수 있도록 설계.

  • 급여 등록
    • 실시간 검색 자동 추가: jQuery Ajax 기반으로 이름/사번 입력 시 Ajax 호출 → 검색 결과를 하단 테이블에 append()
    • 보너스 입력 시 실시간 계산: .on("input") 이벤트로 세금·총액 즉시 재계산 → 테이블과 hidden input 값에 반영
    • 세금 계산 자동화:
      • 과세 소득 = 기본급 + 직책 수당 + 보너스 + OT
      • 공제 = 국민연금(4.5%) + 건강보험(3.5%) + 고용보험(0.9%) + 소득세(8%) + 지방세(10%)
      • 실수령액 = 과세 소득 + 식대 – 공제
    • 데이터 보존: 입력 값을 bonusMap에 저장해 재검색 시에도 값 유지
  • 급여 지급
    • 일괄 지급 처리: 전 직원 데이터를 Ajax + JSON(FormData)로 전송 → Spring Controller @RequestBody로 리스트 수신
    • 다건 Insert 처리: MyBatis <foreach> 구문으로 payroll 테이블에 다건 insert
    • 지급 상태 확인: 지급 완료 후 JSP 테이블의 .statusField 업데이트 → 관리자 즉시 확인

✅ 성과

  • 급여 등록: 실시간 검색 → 선택 → 입력 → 계산이 한 화면에서 가능
  • 급여 지급: 일괄 처리 + 지급 상태 확인으로 실제 인사·회계 팀의 업무 흐름과 일치

🤩 알게 된 점

  • 실시간 반영 로직이 UX 개선에 미치는 효과 체감
  • 다건 insert + 트랜잭션 적용으로 안정적인 급여 지급 보장
  • 업무 프로세스를 단순 기능 구현이 아닌 사용자 관점(UX)에서 설계하는 것의 중요성 학습

4. 품질 검수 / 클레임 처리 로직 혼선

🚨 문제 배경

초기에는 발주 완료 즉시 재고에 등록되도록 구현했는데, 이렇게 하면 검수 과정이 생략되어 불량 수량이 누락되고 재무/재고 데이터가 왜곡되는 문제가 발생.

📌 개선 방향

  • 현업에서는 배송사 API 연동으로 배송완료 자동 처리가 가능하지만, 프로젝트 환경에서는 실제 판매·배송 데이터가 없어 API 사용 불가
  • 따라서 개발 단계에서는 배송완료 상태를 직접 입력하도록 설계 → 이후 검수 테이블로 이동 보장
  • 흐름: 발주 → 배송 → 배송완료 시 검수 → 검수 완료 후 수량 입력 → 합격 수량만 재고 등록 → 부족 수량은 추가 발주

⭐ 해결 방법

  • 배송 완료 버튼을 눌러야 검수 가능하도록 조건 분기
  • 검수 시: 합격 수량만 재고 IN, 불량 수량은 품질 데이터에만 기록 (재무 반영 ❌)
  • 클레임 처리 시:
    • 회수 가능 + 회수 완료 → 재고 IN + 환불 처리
    • 회수 불가 → 환불 처리만, 재고에는 반영 ❌
  • Service 계층에서 분기 로직 구현, Mapper XML에서 상태값별 SQL 분리

🤩 알게 된 점

  • 비즈니스 로직은 DB보다 서비스 계층에서 관리하는 것이 유지보수에 유리
  • 트랜잭션이 데이터 정합성 보장의 핵심임을 직접 경험
  • 실패 시나리오까지 검증하는 습관이 안정적 시스템 운영에 필수
  • SQLD 학습 개념이 실제 프로젝트 의사결정에 실질적으로 도움이 됨

🖥️ TECH STACK

    Spring Boot 3.5: 경량화 된 설정과 내장 Tomcat으로 빠른 개발 환경 구성, REST API 기반 서비스 개발에 활용

    MyBatis: SQL 직접 제어를 통해 복잡한 트랜잭션(발주→재고→출고→재무) 처리 로직을 명확하게 구현

    MySQL 8.0: 외래 키 · 체크 제약 조건 활용으로 데이터 정합성 확보, 트랜잭션 기반 회계 기록 관리

    JSP / JSTL: 빠른 화면 개발과 MVC 패턴 기반 View 단 구현

    jQuery / Ajax: 모달 기반 CRUD, 비동기 캘린더·차트 데이터 갱신에 활용

    Chart.js: 월 별 수익/지출 추세, 품질검수 불량률 등 주요 지표를 시각화하여 대시 보드 구현

    FullCalendar: 휴가 · 근태 일정 관리 달력 구현 (날짜 선택 → 모달 신청 → 즉시 반영)

    Spring Security: 인증 사용자 세션 기반 접근 권한 제어 (관리자 전용 메뉴/기능 분리)

    Redis : 조회 성능 최적화에 활용 @Cacheable+ TTL(10분) 캐시 적용으로 DB 부하 감소 및 응답 속도 55배 개선

    JMeter : 성능 및 부하 테스트 도구 50 → 1000명 동시 사용자 시나리오 테스트를 통해응답 시간 · TPS · Error율 지표를 정량적으로 검증.

👟 TROUBLE SHOOTING

🚨 문제 배경

Toss Payments Webhook 이벤트(CONFIRMED, CANCELED, REFUNDED) 수신 시 동일 이벤트가 여러 번 전송되어 Payment, Invoice, FinanceTransaction이 중복 Insert 되는 문제가 발생했습니다.

  • Toss 정책 상 동일 이벤트를 최대 3회 재전송
  • eventId 중복 검증 부재로 중복 결제 데이터 누적
  • 이중 결제로 인한 회계 데이터 불일치 위험

📌 개선 방향

  • Webhook 이벤트의 멱등성 보장 구조 설계
  • 모든 이벤트를 WebhookLog 테이블에 event_id JSON 그대로 기록
  • 중복 이벤트는 DB Insert 전에 필터링하여 무시
  • Webhook 처리 전체를 @Transactional로 감싸 일관성 보장

⭐ 해결 방법

  • WebhookLog 테이블에 event_id UNIQUE 제약 추가
  • PaymentWebhookService 단계에서 existsByEventId() 검증 후 중복 이벤트 즉시 반환
  • rawPayload 컬럼에 원본 JSON 저장하여 재현 가능성 확보
  • Webhook 성공/실패 로그를 별도로 남겨 장애 원인 추적 강화

✅ 성과

  • 중복 이벤트 처리율 0%, 데이터 불일치 완전 해소
  • Webhook 수신 후 DB 반영까지 평균 1초 이내 단축
  • 장애 원인 추적시간 80% 감소

🤩 알게 된 점

  • 외부 결제 시스템과의 연동에서는 멱등성 보장이 핵심임을 체감
  • 트랜잭션보다 이벤트 단위 일관성 관리가 더 중요함
  • 로깅은 단순 기록이 아닌, 장애 복구의 출발점임을 깨달음

🚨 문제 배경

/api/admin/partner API는 파트너 목록 조회 기능으로, 사용자 수 증가에 따라 반복 호출로 인한 DB 부하와 응답 지연이 심화되었습니다.

  • 평균 응답속도 297ms 이상 (100명 기준)
  • JMeter 1000명 테스트 시 Throughput 저하, TPS 333/sec → 한계 확인
  • 변경이 적은 데이터를 매번 DB에서 조회하는 비효율 발생

📌 개선 방향

  • 조회 빈도 높고 변경 적은 데이터 → Redis 캐시에 저장
  • TTL 60초 설정으로 신선도 유지 및 부하 완화
  • JMeter로 캐시 전/후 성능 비교

⭐ 해결 방법

  • @Cacheable 적용으로 Redis 캐시 활성화
  • GenericJackson2JsonRedisSerializer + JavaTimeModule 등록 → 직렬화 오류 해결
  • TTL 설정: spring.cache.redis.time-to-live=60000 (60초)
  • Docker 기반 Redis 컨테이너 구성으로 로컬 테스트 환경 구축

✅ 성과

  • 응답속도 297ms → 5ms (60배 개선)
  • 캐시 HIT률 85% 이상 유지
  • 3000명 부하 테스트에서도 Error 0%, Throughput 732/sec
  • 서버 CPU 사용률 20% 감소, DB 쿼리 80% 절감

🤩 알게 된 점

  • SQL 튜닝만으로는 한계 → 캐시 전략의 필요성 인식
  • 캐시는 단순 성능 보조가 아니라 DB 생존성 확보 장치
  • 성능 개선은 측정 → 분석 → 검증 → 반복의 결과임을 체감

🚨 문제 배경

JMeter 부하 테스트(250 → 3000명) 결과 Error는 0%였으나 평균 응답속도가 3060ms까지 상승하며 처리 한계가 발생했습니다.

  • Throughput 732/sec, TPS 증가율 둔화
  • GC Overhead Warning 다수 발생
  • HikariCP 커넥션 풀 10개 한계로 병렬 처리 부족

📌 개선 방향

  • HikariCP 최대 커넥션 수 30개로 확장
  • @Async 기반 Webhook 비동기 처리 도입
  • Redis TTL 세분화 (파트너 60초, 대시보드 10초, 인보이스 5분)
  • JPA N+1 제거 및 인덱스 추가로 DB 병목 해소

⭐ 해결 방법

  • WebhookService 내부 Executor 비동기화 처리
  • JMeter 250→3000명 부하 시나리오 재테스트
  • TPS·응답시간 변화 추적

✅ 성과

  • 응답속도 3060ms → 1870ms (40% 단축)
  • Throughput 732/sec → 950/sec (30% 향상)
  • GC Pause Time 42% 감소, 서버 안정성 확보

🤩 알게 된 점

  • 성능 병목은 코드보단 풀링·GC·I/O 구조에서 발생함을 확인
  • 부하 테스트는 확장성 증명의 핵심 도구
  • DB·서버 튜닝은 병행 최적화가 필수

🚨 문제 배경

정기결제 자동화를 위해 Toss Payments API 연동 중 Webhook 서명 검증 실패 및 Sandbox 이벤트 불일치 문제가 반복 발생했습니다.

  • 대시보드 test_wh_**** Secret Key 불일치
  • rawPayload 검증 누락 → Invalid Signature
  • Sandbox 환경 결제 승인 자동 전환 실패
  • 문서와 다른 응답 구조(eventType, data.status)로 직렬화 오류

📌 개선 방향

  • Toss 공식 문서 기반 서명 검증 구조 직접 구현
  • Webhook 원문(payload)을 직렬화 전 별도 저장
  • 모든 이벤트 상태(DONE, APPROVED, CONFIRMED, ... ) 분기 처리
  • Sandbox 환경 Secret Key 통일

⭐ 해결 방법

  • HMAC-SHA256 시그니처 검증 로직 직접 구현 → Toss-Signature 헤더와 서버 계산 결과 비교
  • Webhook JSON 원문을 WebhookLog.payload에 저장 → 재현 가능 구조
  • 테스트 결제는 /webhook 기반으로만 확인, /confirm API는 운영환경 전용으로 분리

✅ 성과

  • Webhook 검증 성공률 100%, 이벤트 누락 0건
  • Sandbox 환경에서도 CONFIRMED 정상 수신
  • Webhook 수신 → DB 반영까지 1초 이내 안정화

🤩 알게 된 점

  • 결제 API는 단순 REST 호출이 아닌 Webhook 기반 비동기 패턴임을 체감
  • 외부 서비스 연동은 코드보다 응답 구조 이해가 중요
  • “성공”보다 정확성이 우선이며, 이를 위해 로그·검증·트랜잭션 세 축이 필요함을 배움
